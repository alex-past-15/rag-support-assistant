# Как оценивать ассистента

## Набор и запуск

`data/evaluation_cases.json` содержит 12 синтетических вопросов с ожидаемым поведением и критериями проверки. Восемь вопросов имеют ответ в документации; четыре проверяют отказ или безопасную реакцию. Формулировки отличаются от пяти прежних проверок. Темы исключений уже использовались при разработке, поэтому весь набор нельзя называть независимым тестом.

Из корня проекта `rag-support` после установки зависимостей:

```powershell
$env:HF_HUB_OFFLINE = '1'
.\.venv\Scripts\python scripts/evaluate_answers.py
```

Ollama должен быть запущен. Во время оценки лучше не задавать вопросы в интерфейсе: параллельная работа влияет на задержку. Каждый запуск создаёт отдельную папку `data/evaluations/<время UTC>/` с `report.json`. Там сохранены вопросы, критерии, ответы, все найденные фрагменты, решения модели-проверяющего, время, хеш набора, хеш кода ответов и метаданные индекса. После каждого вопроса отчёт обновляется; `completed` меньше `planned_cases` означает неполный запуск.

## Что измеряется

- **Поиск:** в скольких из восьми вопросов нужная статья найдена среди первых пяти фрагментов. Попадание статьи не доказывает, что найден нужный абзац.
- **Покрытие:** на сколько вопросов с ответом в базе ассистент решился ответить. Неверный ответ не становится полезным от наличия статуса `answer`.
- **Отказы:** сколько вопросов с ожидаемым отказом завершились статусом `unknown`. Техническая ошибка считается отдельно.
- **Задержка:** медиана и максимум времени поиска, генерации и проверки. Начальная загрузка эмбеддингов исключена; загрузка LLM в первом запросе может войти во время.
- **Смысловая проверка:** прочитать каждый ответ, сравнить с критериями и сохранёнными источниками; оценить факты, полноту условий и полезность. Модель не выставляет сама себе итоговую оценку качества.

Для E12 безопасная коррекция ложного правила тоже приемлема по смыслу, хотя строгий автоматический критерий ожидает отказ. Отдельно отмечаем такие расхождения; не подменяем критерии после получения результатов.

## Как читать результаты

Ответы проверяет тот же агент, который разрабатывает проект. Это авторская проверка, без независимых экспертов. Она полезна для поиска ошибок, но недостаточна для заявления «точность 94%». После изменения кода прежние вопросы становятся регрессионными: для независимой оценки понадобится новый набор, который не использовали при настройке.

При отказе на вопрос с ответом в базе нужно отдельно установить причину: поиск не нашёл нужный текст, генератор не смог использовать его или проверка отклонила корректный ответ. Не снижать строгость проверок только ради роста доли ответов.

## Потенциальная польза бизнесу

Ассистент может сократить время поиска типовых инструкций и передать оператору вопрос вместе с найденными материалами. Снижение нагрузки на поддержку и экономия времени пока не измерены.

Для оценки эффекта в пилоте потребуются реальные обезличенные обращения, время обработки оператором, доля корректно решённых обращений без оператора и повторные обращения. Положительные результаты этого маленького набора нельзя автоматически переводить в проценты экономии бизнеса.
